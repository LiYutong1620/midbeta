## 2 总体概述

### 2.1 软件概述

#### 2.1.1 项目介绍

为满足图文新闻内容的线上发布、全生命周期管理、用户浏览互动、轻量化内容推荐的业务需求，开发一套前后端分离的新闻资讯发布与推荐系统。系统通过 CMS 能力实现内容高效管理，通过 Redis 缓存优化高并发访问性能，通过基础推荐能力提升用户内容浏览体验，同时实现完善的权限控制与内容安全审核能力，适用于媒体、企业、政务机构等主体的新闻资讯内容运营场景。

#### 2.1.2 业务目标与产品价值

##### 2.1.2.1 业务目标

1. **内容管理效率提升**：通过 CMS 能力实现新闻内容的快速发布、编辑、审核，将单篇内容发布时间从传统方式的 30 分钟缩短至 5 分钟以内
2. **用户互动体验优化**：通过评论、点赞、推荐功能，提升用户活跃度，目标日活用户数（DAU）达到注册用户数的 15% 以上
3. **系统性能保障**：通过 Redis 缓存优化，将核心接口响应时间降低 50% 以上，支持≥500 并发用户稳定运行
4. **内容安全合规**：通过敏感词过滤、人工审核机制，保障发布内容 100% 合规，无违规内容前台展示
5. **运营成本降低**：通过自动化的缓存管理、定时任务、日志记录，降低人工运维成本，运维人力投入减少 30% 以上

##### 2.1.2.2 产品价值

1. 用户价值

   - 为普通用户提供便捷的新闻浏览、互动体验，快速获取感兴趣的内容
   - 为管理员提供高效的内容管理工具，降低内容运营的时间成本

   

2. 运营价值

   - 实现内容全生命周期管理，支持内容快速迭代与更新
   - 通过用户行为记录、数据统计，为内容运营决策提供数据支撑
   - 完善的权限控制与审核机制，保障内容安全与合规

   

3. 技术价值

   - 采用成熟的前后端分离架构，模块化设计，支持后续功能快速扩展
   - 通过 Redis 缓存、数据库优化，实现高性能、高可用的系统架构
   - 完善的日志、监控、备份机制，保障系统稳定运行，故障快速恢复

   

#### 2.1.3 产品环境介绍

![系统分层架构图](F:\CourseAssignment\私有云\系统分层架构图.webp)

图1 系统分层架构框图

本系统为独立的 Web 应用产品，采用前后端分离的分层架构设计，无强依赖的外部业务系统，可独立部署运行，也可通过开放 API 集成至更大的内容平台体系中。系统整体环境分为 5 层，各层职责与关联关系如下：

1. **前端展示层**：基于 Vue.js + Element UI/Ant Design Vue 开发，分为用户前台与管理后台，通过 HTTP/HTTPS 协议与后端服务交互
2. **接口服务层**：基于 Spring Boot 开发，提供 RESTful API 接口，包含权限校验、参数校验、流量控制、接口文档能力

#### 3.1.1 R.FUNC.1 用户注册 [P0]

1. **介绍**：实现普通用户的账号注册功能，完成账号合法性校验与信息加密持久化存储

2. 输入

   - 用户名：4-20 位字母、数字、下划线组合，全局唯一
   - 密码：6-20 位字符，需同时包含字母与数字
   - 确认密码：与密码输入值完全一致

   

3. 处理

   - 校验输入参数的合法性，不合法则返回对应错误提示
   - 校验用户名是否已存在，已存在则返回注册失败提示
   - 对密码进行 BCrypt 加盐加密处理，禁止明文存储
   - 将用户信息写入 MySQL 数据库，默认分配「普通用户」角色

   

4. 输出

   - 注册成功：返回 200 状态码与成功提示，引导用户跳转登录页
   - 注册失败：返回对应错误状态码与明确的错误原因（用户名已存在、密码格式错误等）

   

#### 3.1.2 R.FUNC.2 用户登录 [P0]

1. **介绍**：实现用户账号密码登录，完成身份校验与会话凭证发放

2. 输入

   - 用户名：已注册的合法用户名
   - 密码：对应用户名的正确密码

   

3. 处理

   - 校验输入参数的完整性，参数缺失返回错误提示
   - 查询数据库校验用户名是否存在，不存在则返回登录失败
   - 对输入密码进行加密后，与数据库存储的密码比对，不一致则返回登录失败
   - 校验通过后，生成 JWT 会话凭证，记录用户登录状态、角色信息与过期时间

   

4. 输出

   - 登录成功：返回 200 状态码、会话凭证、用户角色、用户基础信息
   - 登录失败：返回对应错误状态码与明确的错误原因

#### 3.3.1 R.FUNC.9 首页新闻列表分页查询 [P0]

1. **介绍**：前台首页展示已发布、已上架的新闻列表，支持分页查询，优先读取 Redis 缓存数据

   - 数据库查询完成后，将结果写入 Redis 缓存，设置默认过期时间 1 小时
   - 对分页参数做合法性校验，参数不合法则使用默认值

   

4. 输出

   - 返回新闻列表数据：新闻 ID、标题、封面、分类名称、发布时间、阅读量、点赞数
   - 返回分页信息：总条数、总页数、当前页码、每页条数

1. **介绍**：用户可按新闻分类筛选对应分类下的新闻列表，支持分页查询

2. 输入

   - 分类 ID：已启用的新闻分类唯一 ID
   - 页码：正整数，默认第 1 页
   - 每页条数：正整数，默认 10 条，最大 50 条

4. 输出

   - 返回对应分类的新闻列表数据与分页信息

   

#### 3.3.3 R.FUNC.11 新闻详情查看 [P0]

1. **介绍**：用户可查看新闻的完整详情内容，优先读取 Redis 缓存数据，降低数据库大文本查询压力

2. **输入**：新闻唯一 ID

3. 处理

   - 校验新闻 ID 的合法性，新闻不存在 / 已下架 / 草稿状态则返回访问失败
   - 优先读取 Redis 中该新闻 ID 对应的详情缓存，缓存存在则直接返回详情数据
   - 缓存不存在时，查询 MySQL 数据库获取新闻完整详情，写入 Redis 缓存，设置默认过期时间 2 小时
   - 新闻详情访问成功后，触发阅读量 + 1 操作（Redis 原子计数器）
   - 登录用户访问时，将该新闻 ID 写入对应用户的最近浏览记录 Redis ZSET 中

   

4. 输出

   - 返回新闻完整详情：新闻 ID、标题、分类、标签、封面、正文、发布时间、发布人、阅读量、点赞数
   - 访问失败：返回对应错误状态码与明确的错误原因

   

#### 3.3.4 R.FUNC.12 新闻阅读量统计 [P0]

1. **介绍**：基于 Redis 原子计数器实现新闻阅读量的累加，定时批量持久化到 MySQL 数据库

2. **输入**：新闻 ID、用户详情页访问行为

3. 处理

   - 新闻详情每次被有效访问，执行 Redis INCR 命令，对该新闻 ID 的阅读量计数器 + 1
   - 系统每 5 分钟执行一次定时任务，批量读取 Redis 中所有新闻的阅读量计数器数据，写入更新到 MySQL 数据库
   - 数据持久化完成后，不重置 Redis 计数器，保证数据连续性
   - 服务正常关闭时，强制执行一次全量计数数据持久化，避免数据丢失

   

4. 输出

   - 实时更新 Redis 中的阅读量数值，定时同步到 MySQL 数据库
   - 新闻列表、详情页展示最新的阅读量数据

   

#### 3.3.5 R.FUNC.13 新闻点赞 / 取消点赞 [P0]

1. **介绍**：登录用户可对新闻执行点赞、取消点赞操作，基于 Redis 原子计数器实现点赞数统计

2. **输入**：新闻 ID、用户 ID、操作类型（点赞 / 取消点赞）

3. 处理

   - 仅登录用户可执行点赞 / 取消点赞操作，未登录则拦截并提示登录
   - 点赞操作：校验用户是否已点赞，未点赞则执行 Redis INCR 命令，对该新闻 ID 的点赞数计数器 + 1，记录用户点赞关联关系
   - 取消点赞操作：校验用户是否已点赞，已点赞则执行 Redis DECR 命令，对该新闻 ID 的点赞数计数器 - 1，删除用户点赞关联关系
   - 系统每 5 分钟执行一次定时任务，批量读取 Redis 中所有新闻的点赞数计数器数据，写入更新到 MySQL 数据库

   

4. 输出

   - 操作成功：返回 200 状态码与成功提示，更新点赞数
   - 操作失败：返回对应错误状态码与明确的错误原因

#### 3.6.1 R.FUNC.20 新闻详情缓存管理 [P0]

#### 3.6.2 R.FUNC.21 阅读量 / 点赞数缓存与持久化 [P0]

1. **介绍**：新闻的阅读量、点赞数使用 Redis 原子计数器累加，定时批量写回数据库，降低数据库高频更新压力

2. **输入**：新闻 ID、计数操作指令（+1/-1）、定时持久化任务

3. 处理

   - 阅读量缓存 key 命名规范：`news:view:count:{新闻ID}`，点赞数缓存 key 命名规范：`news:like:count:{新闻ID}`
   - 数据结构：String 类型，使用 INCR/DECR 命令执行原子计数操作
   - 计数规则：阅读量每次有效访问 + 1，点赞操作 + 1、取消点赞 - 1
   - 持久化规则：系统每 5 分钟执行一次定时任务，批量读取所有计数 key 的数值，更新到 MySQL 数据库对应新闻记录中

   

4. 输出

   - 实时返回最新的计数数值
   - 定时完成计数数据的数据库持久化

   

#### 3.6.3 R.FUNC.22 首页新闻列表缓存管理 [P0]

1. **介绍**：将首页的分页新闻列表结果缓存，降低高频分页查询的数据库压力

2. **输入**：页码、每页条数、列表查询结果、缓存操作指令（写入 / 读取 / 清除）

3. 处理

   - 缓存 key 命名规范：`news:home:list:{页码}:{每页条数}`
   - 缓存数据结构：String 类型，存储列表分页 JSON 数据
   - 缓存写入：首页列表首次查询时，将查询结果写入缓存，默认过期时间 1 小时
   - 缓存读取：首页列表查询时，优先读取对应页码的缓存，命中则直接返回
   - 缓存清除：新闻发布、编辑、上下架、删除时，同步清除所有首页列表相关的缓存 key

   

4. 输出

   - 缓存命中：直接返回首页列表分页数据
   - 缓存未命中：查询数据库并写入缓存后返回数据
   - 缓存清除：成功删除所有首页列表相关的缓存数据

   

#### 3.6.4 R.FUNC.23 用户浏览行为缓存管理 [P1]

1. **介绍**：使用 Redis ZSET 记录用户最近浏览的新闻 ID，实现高性能的行为数据读写

2. **输入**：用户 ID、新闻 ID、时间戳、操作指令（写入 / 查询 / 删除）

3. 处理

   - 缓存 key 命名规范：`user:browse:history:{用户ID}`
   - 数据结构：ZSET 类型，member 为新闻 ID，score 为浏览时间戳
   - 写入规则：用户每次浏览新闻详情，执行 ZADD 更新对应新闻 ID 的 score 为最新时间戳
   - 容量控制：执行 ZREMRANGEBYRANK 命令，仅保留 score 最高的 100 条记录，超出部分自动删除
   - 查询规则：通过 ZREVRANGE 命令获取用户最近浏览的新闻 ID 列表，按时间倒序排列

   

4. 输出

   - 成功写入 / 更新用户浏览行为数据
   - 按要求返回用户最近浏览的新闻 ID 列表

### 5.6 错误处理规范 [P1]

#### 5.6.1 错误码规范

1. **错误码结构**：采用 `{业务域}-{错误类型}-{序号}` 的格式，如 `USER-001`、`NEWS-002`

2. 业务域定义

   - `USER`：用户与权限相关错误
   - `NEWS`：新闻内容相关错误
   - `COMMENT`：评论相关错误
   - `CACHE`：缓存相关错误
   - `SYSTEM`：系统级错误

   

3. 错误类型定义

   - `001-099`：参数校验错误
   - `100-199`：业务逻辑错误
   - `200-299`：权限与认证错误
   - `300-399`：数据相关错误
   - `900-999`：系统级错误

   

4. HTTP 状态码规范

   - `200 OK`：请求成功
   - `400 Bad Request`：参数错误
   - `401 Unauthorized`：未认证
   - `403 Forbidden`：无权限
   - `404 Not Found`：资源不存在
   - `500 Internal Server Error`：系统内部错误

   

#### 5.6.2 错误响应格式

所有错误响应必须采用统一的 JSON 格式，示例如下：

```
{
  "code": "USER-001",
  "message": "用户名已存在",
  "data": null,
  "timestamp": 1710000000000,
  "requestId": "req-abc123def456"
}
```

字段说明：

- `code`：业务错误码
- `message`：用户友好的错误提示信息
- `data`：错误相关的补充数据（可选）
- `timestamp`：错误发生的时间戳
- `requestId`：请求唯一标识，用于问题追踪

#### 5.6.3 错误提示规范

1. **用户端提示**：面向普通用户的错误提示必须简洁、友好、无技术术语，明确告知用户问题原因与解决建议
2. **管理端提示**：面向管理员的错误提示可包含必要的技术信息，便于管理员定位问题
3. **提示语言**：所有错误提示统一使用中文，无英文提示
4. **异常场景引导**：对于可恢复的错误，必须提供明确的解决引导，如「请稍后重试」、「请检查网络连接」

#### 5.6.4 异常日志规范

1. 所有异常必须记录日志，包含异常类型、异常堆栈、请求参数、请求标识、操作人、操作时间等完整信息

2. 日志分级规范：

   - `ERROR`：系统级错误、业务异常，需立即处理
   - `WARN`：警告信息，如参数不合法、缓存未命中
   - `INFO`：关键业务操作记录，如用户登录、内容发布
   - `DEBUG`：调试信息，开发调试时使用

   

3. 日志必须支持按时间、级别、业务域、请求标识检索，便于问题排查

4. 敏感信息（如密码、用户隐私数据）在日志中必须脱敏处理

#### 5.6.5 错误恢复机制

1. **接口重试机制**：对于临时性错误（如网络波动、缓存超时），接口必须支持自动重试，重试次数不超过 3 次
2. **降级机制**：当 Redis 缓存服务故障时，系统必须自动降级直连数据库，保证核心功能可用
3. **熔断机制**：当某个接口错误率超过阈值（如 50%）时，必须触发熔断，避免雪崩效应
4. **数据一致性保障**：当操作失败时，必须保证数据一致性，支持事务回滚，无脏数据、半更新数据

#### 6.6.2 数据归档策略

1. 归档触发条件

   - 操作日志：超过 6 个月的日志
   - 已删除的新闻 / 评论：逻辑删除超过 1 年的数据
   - 过期的用户浏览历史：超过 1 年的浏览记录

   

2. 归档方式

   - 采用冷归档方式，将归档数据从主库迁移至归档库
   - 归档数据保留原始结构，支持查询与恢复，但不支持修改

   

3. 归档存储

   - 归档库采用独立的数据库实例，与主库物理隔离
   - 归档数据存储成本较低的存储介质（如 SATA 硬盘）

   

4. 归档周期

   - 每月执行一次归档任务，在业务低峰期（如凌晨 2 点）执行
   - 归档任务执行前必须完成主库全量备份

   

5. 归档数据保留期限

   - 操作日志：归档后保留 3 年
   - 其他业务数据：归档后永久保留

   

#### 6.6.3 缓存预热策略

1. 预热触发时机

   - 系统启动 / 重启时
   - 缓存大规模失效后
   - 业务高峰期前（如早 8 点、晚 8 点）

   

2. 预热数据范围

   - 热点新闻详情：最近 7 天发布的、阅读量 Top 1000 的新闻
   - 首页列表：前 5 页的新闻列表数据
   - 系统配置、分类列表、标签列表等基础数据

   

3. 预热方式

   - 系统启动时自动执行预热任务
   - 支持手动触发预热任务
   - 预热任务采用异步方式执行，不影响系统启动速度

   

4. 预热监控

   - 预热任务执行过程中必须记录日志，包含预热数据量、执行耗时、成功 / 失败状态
   - 预热完成后必须验证缓存命中率，确保预热效果

   

#### 6.6.4 数据清理策略

1. 日志清理

   - 应用日志：超过 30 天的日志文件自动删除
   - 操作日志：主库中超过 6 个月的日志自动归档后删除

   

2. 临时数据清理

   - 上传的临时图片文件：超过 24 小时未使用的自动删除
   - 缓存过期数据：Redis 自动淘汰过期的缓存数据

   

3. 测试数据清理

   - 测试环境支持一键清理测试数据，重置为初始状态
   - 测试数据清理必须在非测试时段执行，避免影响测试

   

4. 清理任务执行

   - 所有清理任务采用定时任务方式执行，在业务低峰期执行
   - 清理任务执行前必须记录日志，执行后必须验证清理结果

   

#### 6.6.5 数据迁移策略

1. 迁移场景

   - 系统版本升级，数据库结构变更
   - 服务器迁移，数据库实例更换
   - 数据量增长，数据库分库分表

   

2. 迁移方式

   - 采用在线迁移方式，迁移过程中系统不停止服务
   - 迁移前必须完成全量备份，迁移后必须验证数据一致性

   

3. 迁移流程

   - 制定详细的迁移计划与回滚方案
   - 在测试环境进行迁移演练，验证迁移方案可行性
   - 在业务低峰期执行迁移
   - 迁移完成后进行数据校验、功能验证、性能验证
   - 验证通过后正式切换，保留旧环境至少 7 天

   

4. 回滚机制

   - 迁移过程中出现问题时，必须立即停止迁移，执行回滚方案
   - 回滚后必须验证系统功能与数据一致性

4. 接口设计必须遵循 RESTful 规范，统一请求 / 响应格式，无自定义的非标接口格式
